# Аккаунты Spell and Iron Rift

Rift — единственная система игровой авторизации проекта. Microsoft OAuth, Xbox Live и привязка к купленному Minecraft-профилю не используются. Клиент запускает Minecraft с offline-профилем, а право входа подтверждается одноразовым билетом Rift.

## Модель авторизации

| Что | Чем подтверждается |
|---|---|
| Игровая личность | Аккаунт Rift: ник и постоянный UUID аккаунта |
| Право подключиться к серверу | Одноразовый Game Ticket, выданный backend после проверки Rift-сессии |
| Подлинность сервера | Секретный `serverKey`, известный backend и серверному моду |
| Роли и баны | Backend Rift |

## Поток входа

1. Игрок регистрируется или входит в лаунчере по нику и паролю Rift.
2. Лаунчер хранит долгоживущую сессию в зашифрованном хранилище ОС.
3. Перед запуском лаунчер проверяет сессию через `/api/account/me`, обновляет файлы сборки и устанавливает Minecraft/NeoForge при необходимости.
4. Непосредственно перед запуском лаунчер запрашивает `POST /api/account/game-session`. Backend выдаёт случайный одноразовый билет с TTL 60 секунд.
5. Лаунчер передаёт билет процессу Minecraft через переменную окружения `RIFT_GAME_TICKET`. Билет не записывается в `launcher.json`, аргументы Java или логи лаунчера.
6. Клиентский мод отправляет билет серверу отдельным NeoForge-пакетом.
7. Серверный Guard отправляет билет в `POST /api/server/auth/consume` с приватным заголовком `x-rift-server-key`, `serverId` и игровым ником.
8. Backend проверяет срок действия, сервер, ник, одноразовость билета и актуальный статус аккаунта. При успехе сервер применяет роль и отображаемый ник; иначе отключает игрока.

## Что реализовано в аккаунтах

- Ники 3–16 символов: латиница, цифры и `_`; уникальность без учёта регистра.
- Постоянный UUID аккаунта.
- Пароли хранятся как Argon2id-хеши; backend не хранит исходный пароль.
- Сессии Rift ротируются при обновлении и хранятся в лаунчере через Electron `safeStorage`.
- Временный пароль от администратора требует смены перед игрой.
- Бан отзывает сессии; ранее выданный билет также не пройдёт проверку после бана.
- Билеты одноразовые, привязаны к `serverId` и нику, срок жизни — 60 секунд.
- Игровой сервер обязан предъявить свой приватный ключ. Пустой или неверный ключ отклоняется.
- Сервер работает в `online-mode=false`; Minecraft offline UUID используется только как техническая транспортная идентичность и не считается доказательством аккаунта.

## Важное ограничение текущего сетевого этапа

В текущей реализации клиент отправляет билет в событии входа игрока, а Guard проверяет его сразу после появления игрока на сервере. На время проверки игрок неуязвим, а если билет не пришёл за 10 секунд — соединение закрывается. Это post-login guard, а не строгая проверка до создания игрока в мире; для публичного сервера следующий этап — перенести обмен билетом в NeoForge configuration/login negotiation pipeline.

## Настройка

1. Запустите backend. Он создаёт приватный ключ сервера в `data/keys/server-api.key`. Владелец может получить его в Rift Control → «Аккаунты игроков» → ключ игрового сервера.
2. В `launcher/config/app.json` укажите HTTPS-адрес backend в `apiBase` и публичные ключи подписи манифеста в `trustedManifestKeys`. Azure Client ID не нужен.
3. Установите `spellironrift-guard-*.jar` на выделенный NeoForge-сервер.
4. Первый запуск создаст `config/spellironrift-guard.json`. Заполните:
   ```json
   {
     "apiBase": "https://rift.example.org",
     "serverKey": "<секретный ключ из Rift Control>",
     "serverId": "main",
     "moderatorOpLevel": 3,
     "adminOpLevel": 4
   }
   ```
5. В `server.properties` установите:
   ```properties
   online-mode=false
   enforce-secure-profile=false
   ```
6. Перезапустите сервер. Без настроенного Guard сервер не должен считаться защищённым; Guard работает fail-closed и не пускает игроков без валидного билета.

Если backend недоступен, новые подключения не проходят проверку. Кэш старых Mojang UUID больше не используется.

## Playit

Playit отвечает только за сетевой туннель к Minecraft TCP-порту. Он не участвует в авторизации Rift и не заменяет Game Ticket. Публичный Playit hostname и порт должны совпадать с адресом сервера в опубликованном манифесте: клиент отправляет билет только на настроенный адрес проекта. Если туннель пробрасывает порт сервера, игроки подключаются к выданному Playit адресу, а Guard проверяет билет через backend.
